# ADR-0005: Поиск по нормативам — эмбеддинги, гибридный поиск, схема фрагментов

- Статус: предложено
- Дата: 2026-10-30
- Участники: Подтуров Павел (автор), Claude (Anthropic) — соавтор
- Задача: #19

## Контекст

- Хранилище уже выбрано: PostgreSQL 17 + pgvector, отдельной векторной базы нет ([ADR-0004](0004-vector-storage.md)).
- Векторы считаются через LLM Gateway, нормативы загружаются в базу разовым скриптом ([архитектура бэкенда](../backend-architecture.md)).
- Потребители — агенты-чекеры ([ADR-0003](0003-agent-orchestration.md)). Им нужен конкретный пункт норматива со ссылкой для цитирования. Инструменты: `search_fgos`, `get_fgos_clause`, `search_spbu_regulations`, `get_spbu_clause`, `search_prof_standards`, `search_all_regulations`.
- Корпус маленький, сотни–тысячи фрагментов: ФГОС, Образовательный стандарт СПбГУ, профстандарты.
- Документы русскоязычные, с иерархической нумерацией (раздел → пункт → подпункт) и кодами: `УК-1`, `ОПК-3`, `06.001`.

## Решение

1. **Фрагмент = пункт норматива.**
   - Документ режется по собственной нумерации; путь по разделам сохраняется.
   - Длинный пункт делится по предложениям без потерь: все части получают `id` этого пункта и свой номер `part`, а конкатенация частей в порядке `part` даёт исходный текст пункта дословно.
   - Произвольные окна фиксированной длины не используем.

   Обоснование: нарезка по структуре закона даёт лучший recall на немецком ГК [4], а в работе StrucChunk на основную часть выигрыша приходится именно она [5]. На регламентах выбор нарезки заметно влияет на качество поиска [6].

2. **Модель эмбеддингов — BGE-M3** (BAAI): открытые веса, лицензия MIT, вектор 1024, вход до 8192 токенов [1].
   - Запускается локально через **Ollama** (модель `bge-m3`) за LLM Gateway, поэтому нормативы и запросы не уходят к внешнему провайдеру. Ollama уже предусмотрен в стеке (профиль `local-llm` в `compose.yaml`, см. [архитектуру](../architecture.md)), нового сервиса не появляется — в духе [ADR-0004](0004-vector-storage.md), который выбирал pgvector, чтобы не добавлять компоненты.
   - Эмбеддинги нужны всегда, в том числе при внешнем LLM-провайдере, поэтому Ollama должен быть доступен и без профиля `local-llm`.
   - Клиент передаёт `truncate: false` и явный `options.num_ctx` (8192): по умолчанию Ollama обрезает слишком длинный вход, и пункт мог бы молча потерять конец.
   - Модуль `llm/` предоставляет единый метод батчевой генерации эмбеддингов: список строк на входе, список векторов размерности 1024 на выходе. Через него ходят и скрипт загрузки нормативов, и RAG-поиск (запрос — батч из одной строки). Метод использует общие механизмы шлюза (ретраи, лимиты), дополнительно делит вход на пачки и проверяет размерность. Другие модули за эмбеддингами к Ollama напрямую не обращаются.

   Обоснование: на русском бенчмарке RusBEIR это лучшая одиночная плотная модель — 61.13 nDCG@10 в среднем по 17 наборам [2]. Длинный вход позволяет не резать большинство пунктов.

3. **Гибридный поиск в одном SQL-запросе.**
   - Два списка кандидатов: полнотекстовый (`tsvector`, конфигурация `russian`) и векторный (pgvector, косинусное расстояние).
   - Списки объединяются через **Reciprocal Rank Fusion** [7]. RRF складывает ранги, а не оценки, поэтому разная шкала `ts_rank` и косинуса не мешает.
   - Фильтры по типу документа, `doc_id` и редакции — в `WHERE`.
   - При нашем объёме векторный поиск идёт точным перебором, без ANN-индекса. HNSW добавим, если корпус вырастет.

   Обоснование: на русском BM25 остаётся сильной базой и на длинных документах обходит нейросетевые модели [2]; в юридическом поиске гибрид повышает recall у моделей без дообучения [8]; связка «BM25 + BGE-M3 через RRF» используется для юридических документов [5].

4. **Коды и номера пунктов ищутся точно, а не семантически.**
   - Коды из текста пункта хранятся отдельным полем в нормализованном виде: регистр, пробелы, одинаковые по виду кириллические и латинские буквы приводятся к одному написанию; точки и дефисы сохраняются.
   - Нормализация — одна общая функция в `src/`. Ею пользуются и загрузка нормативов, и извлечение кодов из РПД, иначе `УК-1` из РПД и из базы нормативов могут не совпасть.
   - Если в запросе есть код или номер пункта, сначала выполняется точный поиск по этому полю (`method=exact`).
   - Код вроде `УК-1` есть в каждом ФГОС, поэтому `doc_id` для такого запроса не обязателен, но без него точный поиск возвращает все совпадения, и у каждого указаны `doc_id` и `edition`. Чекер, которому нужен конкретный документ, передаёт `doc_id`.
   - Если точных совпадений нет, поиск продолжается как гибридный, а результаты помечаются `method=hybrid`. Для запроса с кодом такие результаты не подтверждают, что требование к этому коду существует (например, для кода ПКП программы или индикатора `УК-1.2`, которых в нормативах нет). Это прямо указывается в описании инструмента для агента.

   Обоснование: при правильной нарезке номера разделов в запросе находятся точным совпадением [5]. А удаление пунктуации при предобработке текста (так сделано для BM25 в RusBEIR [2]) такие коды разрушает.

5. **Переранжирование пока не вводим.** Кандидат на будущее — `bge-reranker-v2-m3`: на RusBEIR он поднимает BGE-M3 с 61.13 до 65.85 nDCG@10 [2]. Добавим, если на запросах ФГОС-чекера правильный пункт будет находиться, но стоять ниже первых мест.

### Схема хранения (таблица в `dao/`, миграция Alembic)

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `text` | Ссылка на пункт для цитирования, например `fgos-02.03.02:2.3`; редакцию не содержит |
| `doc_type` | `text` | `fgos` / `spbu_standard` / `prof_standard` — фильтр для `search_*` |
| `doc_id`, `edition` | `text` | Документ и редакция (реквизиты приказа, дата) |
| `path` | `text` | Путь по разделам: «Раздел II › п. 2.3» |
| `part` | `int` | Номер части, если пункт разделён (иначе 0) |
| `text` | `text` | Текст пункта (у разделённого пункта — текст своей части) |
| `codes` | `text[]` | Нормализованные коды из пункта |
| `embedding` | `vector(1024)` | Эмбеддинг BGE-M3 от строки «путь + текст» |
| `tsv` | `tsvector` | Генерируемая колонка `to_tsvector('russian', path \|\| ' ' \|\| text)` |

Первичный ключ — `(id, edition, part)`: `id` одинаков у разных редакций одного документа и у частей одного пункта.

Индексы:
- GIN по `tsv` — быстрый полнотекстовый поиск;
- GIN по `codes` — точный поиск по кодам (`codes @> ...`);
- btree по `(doc_id, edition)` — фильтры в `WHERE`;
- по `embedding` индекса нет: точный перебор (см. решение 3).

### Интерфейс инструментов

Инструменты `search_*` и `get_*_clause` реализует модуль `retrieval/`; таблица и миграция живут в `dao/`; вектор запроса считается единым методом из `llm/` (решение 2).

`search_*(query, doc_id?, edition?, top_k)`:

- `doc_id` и `edition` — необязательные фильтры. Без `edition` поиск идёт по всем загруженным редакциям.
- ФГОС-чекер определяет `doc_id` по коду направления: его отдаёт `get_program_metadata` ([ADR-0003](0003-agent-orchestration.md)), в данных программы это `ProgramInfo.direction_code`. Поле необязательное и есть не в каждой РПД. Если код направления не определён, чекер не ищет по ФГОС без фильтра (в выдачу попали бы чужие ФГОС), а сообщает подграфу о недостающих данных. Оркестратор запрашивает их у пользователя (раздел «Обращения к пользователю» в ADR-0003); без ответа проверка по ФГОС остаётся неполной.
- По каждому найденному пункту возвращаются: `id`, `path`, `text`, `doc_id`, `edition`, `rank` и `method` (`exact` / `hybrid`). Оценку RRF не отдаём: она зависит от ранга и несопоставима между запросами. Порог по оценке в чекерах не используется.
- `text` возвращается дословно, без нормализации и сокращений: кодовая проверка замечаний (ADR-0003) может сверять цитату с текстом пункта.
- Пункт, разбитый на части, возвращается целиком одним результатом: `text` — все части в порядке `part`, `rank` определяется лучшей из частей. Ранжирование идёт по частям, дублей одного пункта в выдаче нет.

`get_*_clause(id, edition)` возвращает полный текст пункта вместе с путём — ровно той редакции, которая указана. Значения `id` и `edition` чекер берёт из результата `search_*`, поэтому найденный текст и цитата относятся к одной редакции.

## Рассмотренные варианты

- **Отдельная векторная база (Qdrant, Chroma)** — отклонено в [ADR-0004](0004-vector-storage.md).
- **multilingual-E5-large(-instruct)** — по качеству на русском близок к BGE-M3 [2], но вход ограничен 512 токенами: длинные пункты пришлось бы резать.
- **USER-bge-m3** (адаптация BGE-M3 под русский) — среди лучших на RusBEIR [2]; **FRIDA** — высокая общая оценка Russian MTEB (70.95), но это среднее по всем задачам, а не только по поиску [3]. Оставляем как запасные варианты.
- **Qwen3-Embedding** (Apache 2.0) и **Giga-Embeddings** — сильны по общим оценкам Russian MTEB [3], но лидируют их версии на несколько миллиардов параметров. Для корпуса из сотен пунктов это лишнее.
- **Эмбеддинги по API внешнего провайдера** — дешевле в запуске, но нормативы и запросы уходят наружу, появляется плата и зависимость от провайдера.
- **Hugging Face Text Embeddings Inference (TEI) как отдельный сервис** — специализированный сервер эмбеддингов: батчи, запуск моделей напрямую с Hugging Face Hub, поддержка reranker-моделей. Но это ещё один сервис в `compose.yaml`, а Ollama уже в стеке. К TEI вернёмся, если понадобится переранжирование (решение 5) или Ollama не справится с нагрузкой. Благодаря единому методу в `llm/` замена рантайма не затронет скрипт загрузки и RAG.
- **Только векторный или только полнотекстовый поиск** — каждый проигрывает на своём типе запросов: векторный — на кодах и точных формулировках, полнотекстовый — на перефразировках [2], [5], [8].

## Последствия

- Одна база и одна миграция: фрагменты, векторы и полнотекстовый индекс лежат вместе с моделью ОП.
- У каждого результата есть устойчивая ссылка на пункт (`id` + `edition`), а значит — цитирование в отчётах чекеров.
- Модель эмбеддингов работает в том же Ollama, что и локальная LLM: около 0,6 млрд параметров, CPU достаточно. Ollama становится обязательным сервисом развёртывания, а не только опциональным профилем `local-llm`; модель `bge-m3` загружается при установке.
- Клиент для эмбеддингов пишется один раз, в `llm/`. Скрипт загрузки и RAG пользуются одним методом, поэтому смена рантайма или модели не затрагивает их код.
- Смена модели означает перегенерацию векторов скриптом загрузки, а при другой размерности — ещё и миграцию колонки `embedding`.
- Полнотекстовый поиск PostgreSQL — не BM25. Для RRF это неважно, но сравнивать с цифрами статей напрямую нельзя.
- В [ADR-0003](0003-agent-orchestration.md) инструменты `get_*_clause` описаны как «по ссылке», сигнатуры `search_*` не заданы, использование `method` и запрос недостающего кода направления не описаны. Это нужно обновить отдельным изменением.
- Выбор модели и необходимость переранжирования проверяем на первых реальных запросах ФГОС-чекера при реализации поиска по ФГОС.
