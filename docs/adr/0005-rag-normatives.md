# ADR-0005: Поиск по нормативам — эмбеддинги, гибридный поиск, схема фрагментов

- Статус: предложено
- Дата: 2026-10-30
- Участники: Подтуров Павел (автор), Claude (Anthropic) — соавтор
- Задача: #19

## Контекст

- Хранилище уже выбрано: PostgreSQL 17 + pgvector, отдельной векторной базы нет ([ADR-0004](0004-vector-storage.md)).
- Векторы считаются через LLM Gateway, нормативы загружаются в базу разовым скриптом ([архитектура бэкенда](../backend-architecture.md)).
- Потребители — агенты-чекеры ([ADR-0003](0003-agent-orchestration.md)). Им нужен конкретный пункт норматива со ссылкой для цитирования. Инструменты: `search_fgos`, `get_fgos_clause`, `search_spbu_regulations`, `search_prof_standards`, `search_all_regulations`.
- Корпус маленький, сотни–тысячи фрагментов: ФГОС, Образовательный стандарт СПбГУ, профстандарты.
- Документы русскоязычные, с иерархической нумерацией (раздел → пункт → подпункт) и кодами: `УК-1`, `ОПК-3`, `06.001`.

## Решение

1. **Фрагмент = пункт норматива.**
   - Документ режется по собственной нумерации; путь по разделам сохраняется.
   - Длинный пункт делится по предложениям, все части получают ID этого пункта.
   - Произвольные окна фиксированной длины не используем.

   Обоснование: нарезка по структуре закона даёт лучший recall на немецком ГК [4], а в работе StrucChunk на основную часть выигрыша приходится именно она [5]. На регламентах выбор нарезки заметно влияет на качество поиска [6].

2. **Модель эмбеддингов — BGE-M3** (BAAI): открытые веса, лицензия MIT, вектор 1024, вход до 8192 токенов [1].
   - Запускается локально (например, Ollama или Hugging Face TEI) за LLM Gateway, поэтому нормативы и запросы не уходят к внешнему провайдеру.

   Обоснование: на русском бенчмарке RusBEIR это лучшая одиночная плотная модель — 61.13 nDCG@10 в среднем по 17 наборам [2]. Длинный вход позволяет не резать большинство пунктов.

3. **Гибридный поиск в одном SQL-запросе.**
   - Два списка кандидатов: полнотекстовый (`tsvector`, конфигурация `russian`) и векторный (pgvector, косинусное расстояние).
   - Списки объединяются через **Reciprocal Rank Fusion** [7]. RRF складывает ранги, а не оценки, поэтому разная шкала `ts_rank` и косинуса не мешает.
   - Фильтры по типу документа и редакции — в `WHERE`.
   - При нашем объёме векторный поиск идёт точным перебором, без ANN-индекса. HNSW добавим, если корпус вырастет.

   Обоснование: на русском BM25 остаётся сильной базой и на длинных документах обходит нейросетевые модели [2]; в юридическом поиске гибрид повышает recall у моделей без дообучения [8]; связка «BM25 + BGE-M3 через RRF» используется для юридических документов [5].

4. **Коды и номера пунктов ищутся точно, а не семантически.**
   - Коды из текста пункта хранятся отдельным полем в нормализованном виде: регистр, пробелы, одинаковые по виду кириллические и латинские буквы приводятся к одному написанию; точки и дефисы сохраняются.
   - Если в запросе есть код или номер пункта, сначала выполняется точный поиск по этому полю.

   Обоснование: при правильной нарезке номера разделов в запросе находятся точным совпадением [5]. А удаление пунктуации при предобработке текста (так сделано для BM25 в RusBEIR [2]) такие коды разрушает.

5. **Переранжирование пока не вводим.** Кандидат на будущее — `bge-reranker-v2-m3`: на RusBEIR он поднимает BGE-M3 с 61.13 до 65.85 nDCG@10 [2]. Добавим, если на запросах ФГОС-чекера правильный пункт будет находиться, но стоять ниже первых мест.

### Схема хранения (таблица в `dao/`, миграция Alembic)

| Поле | Тип | Назначение |
| --- | --- | --- |
| `id` | `text`, PK | Ссылка для цитирования, например `fgos-02.03.02:2.3` |
| `doc_type` | `text` | `fgos` / `spbu_standard` / `prof_standard` — фильтр для `search_*` |
| `doc_id`, `edition` | `text` | Документ и редакция (реквизиты приказа, дата) |
| `path` | `text` | Путь по разделам: «Раздел II › п. 2.3» |
| `part` | `int` | Номер части, если пункт разделён (иначе 0) |
| `text` | `text` | Текст пункта |
| `codes` | `text[]` | Нормализованные коды из пункта |
| `embedding` | `vector(1024)` | Эмбеддинг BGE-M3 от строки «путь + текст» |
| `tsv` | `tsvector` | Генерируемая колонка `to_tsvector('russian', path || ' ' || text)` |

Инструменты `search_*` возвращают по каждому найденному пункту: `id`, `path`, `text`, `doc_id`, `edition`, оценку и способ совпадения (`exact` / `hybrid`). `get_*_clause(id)` возвращает полный текст пункта вместе с путём.

## Рассмотренные варианты

- **Отдельная векторная база (Qdrant, Chroma)** — отклонено в [ADR-0004](0004-vector-storage.md).
- **multilingual-E5-large(-instruct)** — по качеству на русском близок к BGE-M3 [2], но вход ограничен 512 токенами: длинные пункты пришлось бы резать.
- **USER-bge-m3** (адаптация BGE-M3 под русский) — среди лучших на RusBEIR [2]; **FRIDA** — высокая общая оценка Russian MTEB (70.95), но это среднее по всем задачам, а не только по поиску [3]. Оставляем как запасные варианты.
- **Qwen3-Embedding** (Apache 2.0) и **Giga-Embeddings** — сильны по общим оценкам Russian MTEB [3], но лидируют их версии на несколько миллиардов параметров. Для корпуса из сотен пунктов это лишнее.
- **Эмбеддинги по API внешнего провайдера** — дешевле в запуске, но нормативы и запросы уходят наружу, появляется плата и зависимость от провайдера.
- **Только векторный или только полнотекстовый поиск** — каждый проигрывает на своём типе запросов: векторный — на кодах и точных формулировках, полнотекстовый — на перефразировках [2], [5], [8].

## Последствия

- Одна база и одна миграция: фрагменты, векторы и полнотекстовый индекс лежат вместе с моделью ОП.
- У каждого результата есть устойчивая ссылка на пункт, а значит — цитирование в отчётах чекеров.
- Модель эмбеддингов нужно развернуть за LLM Gateway: около 0,6 млрд параметров, работает на CPU.
- Смена модели означает перегенерацию векторов скриптом загрузки, а при другой размерности — ещё и миграцию колонки `embedding`.
- Полнотекстовый поиск PostgreSQL — не BM25. Для RRF это неважно, но сравнивать с цифрами статей напрямую нельзя.
- Выбор модели и необходимость переранжирования проверяем на первых реальных запросах ФГОС-чекера при реализации поиска по ФГОС.
