# ADR-0002: Извлечение сущностей — гибрид правил и LLM с валидацией

- Статус: предложено
- Дата: 2026-10-15
- Участники: Измайлов Никита (автор), остальные — TBD

## Контекст

Модулю `extraction/` нужно из Markdown-версий документов ОП (РПД, учебный план,
характеристика программы) получить структурированную модель программы:
компетенции, индикаторы, дисциплины, семестры, трудоёмкость, формы контроля,
результаты обучения, оценочные средства (требование №2 в `docs/project-review.md`).

Ограничения и наблюдения:

- Вход — Markdown. Значительная часть полей лежит в таблицах (коды компетенций,
  часы, з.е., семестры, формы контроля), остальное — свободный текст
  (результаты обучения, оценочные средства, формулировки индикаторов).
- Каждая сущность должна ссылаться на источник (документ, раздел, цитата),
  иначе протокол проверки не будет объяснимым.
- Эталонной разметки пока нет (датасет A появится позже), поэтому методы,
  требующие обучения, сейчас не применимы.
- Ориентиры по качеству из разбора проекта: коды и числа из таблиц ≥ 0.95,
  текстовые поля ≥ 0.8.
- LLM-провайдер ещё не выбран, значит, зависимость от него нужно держать
  за единым шлюзом `llm/`.

## Решение

Гибридный пайплайн из трёх частей:

1. **Детерминированный разбор.** Дерево заголовков Markdown, парсер таблиц,
   классификация таблиц по заголовкам столбцов, нормализация кодов
   (`УК 1`, `УК–1` → `УК-1`). Отвечает за коды, числа, семестры и формы контроля.
2. **LLM со структурированным выводом** для текстовых полей и нестандартных
   таблиц. Pydantic-схема, температура 0, секция документа на вызов,
   повтор до 2 раз при невалидном JSON, обязательная цитата-доказательство,
   которую код проверяет по исходному тексту. Вызовы — только через `llm/`.
3. **Валидация кодом.** Суммы часов и пересчёт з.е., существование кодов
   компетенций из LLM-ответа в таблице компетенций, совпадение цитат с текстом.
   Расхождения попадают в `warnings`, а сомнительные сущности помечаются
   как «требует ручной проверки».

Результат — Pydantic-модель программы со ссылками на источники у каждой сущности.

## Рассмотренные варианты

| Вариант | Плюсы | Минусы |
| --- | --- | --- |
| Только правила (regex, таблицы) | быстро, бесплатно, детерминированно | не берёт свободный текст, хрупко к шаблонам |
| Только LLM со схемой | любой шаблон, быстрый старт | стоимость, ошибки в числах и кодах, недетерминированность |
| Мультипроходная самопроверка LLM | выше полнота и точность на тексте | стоимость ×2–3; рассматриваем как надстройку, если метрики ниже порогов |
| Готовые IE-библиотеки (LangExtract, `instructor`) | чанкинг и привязка к источнику из коробки | зависимость от внешнего API, меньше контроля над таблицами; `instructor` можем использовать внутри п. 2 |
| Zero-shot NER (GLiNER и аналоги) | локально, бесплатно на инференсе | качество на русском доменном тексте неизвестно, нет структуры и связей |
| Дообучение (ruBERT NER, LoRA для малой LLM) | дешёвый инференс, локальный запуск | нужна разметка (датасет A), GPU; преждевременно до M3 |

## Последствия

**Плюсы**

- Точность на формальных полях близка к 1.0, LLM тратится только там, где она нужна.
- Валидация кодом ловит галлюцинации и ошибки парсинга до этапа проверок.
- Не привязываемся к провайдеру: LLM-часть работает через `llm/`.
- Модель со ссылками на источники напрямую используется в протоколе.

**Цена**

- Два пути кода и стык между ними, поддерживать их сложнее.
- Правила чувствительны к шаблонам документов: на новом шаблоне нужна доработка.
- Качество разбора зависит от конвертации в Markdown (объединённые ячейки,
  многостраничные таблицы).
- Для замера нужен датасет A; до его появления оценка идёт на синтетических
  фикстурах и небольшой ручной выборке.

**Дальше**

- Замерить метрики на датасете A и при необходимости добавить самопроверку LLM.
- Вернуться к дообучению и GLiNER после M3, если качество или стоимость не устроят.
- Выбор LLM-провайдера оформить отдельным ADR.

## Оценка работ

Ориентировочно 12–18 рабочих дней одного разработчика на связку из трёх частей,
без учёта разметки данных.
