# ADR-0004: Векторное хранилище — pgvector

- Статус: предложено
- Дата: 2026-10-28
- Участники: Епишкин Роман (автор)

## Контекст
В системе `edu-doc-agent` должен быть реализован гибридный поиск (RAG) по нормативным документам (ФГОС, профстандарты, регламенты вуза) для проверки образовательных программ. Нам требуется выбрать инструмент для хранения эмбеддингов документов и выполнения быстрого векторного поиска, учитывая ограничения архитектуры single-node MVP и стремление к минимализму инфраструктуры.

## Решение
Использовать расширение **pgvector** для уже развёрнутой базы данных PostgreSQL 17.

## Рассмотренные варианты
- **pgvector (выбрано):**
  - *Плюсы:* Единый источник истины (Source of Truth). Векторные данные лежат в той же БД, что и диалоги, статусы задач и модели ОП. Транзакционная целостность, отсутствие новых компонентов в Docker Compose, общие бэкапы.
  - *Минусы:* Хуже масштабируется на миллиардах векторов по сравнению с выделенными решениями, но объём наших нормативных документов исчисляется сотнями, что полностью нивелирует этот недостаток.
- **Qdrant:**
  - *Плюсы:* Мощный специализированный движок, отличная масштабируемость, богатые возможности фильтрации по payload.
  - *Минусы:* Усложнение инфраструктуры (новый сервис, свои бэкапы, мониторинг), явный оверинжиниринг для текущих масштабов MVP.
- **Chroma:**
  - *Плюсы:* Лёгкий старт, удобная интеграция в экосистему LangChain и Python для локальной разработки.
  - *Минусы:* Менее стабильна в production-среде как клиент-серверное решение по сравнению с PostgreSQL; плодит сущности (появление второго хранилища).

## Последствия
Использование `pgvector` позволяет сохранить модульный монолит максимально простым с точки зрения эксплуатации. Схема управляется Alembic, а данные и векторы резервируются единым механизмом PostgreSQL (pg_dump или физические бэкапы). Издержки — незначительное увеличение вычислительной нагрузки на узел PostgreSQL при векторном поиске, что не является критичным для текущего объёма данных.
